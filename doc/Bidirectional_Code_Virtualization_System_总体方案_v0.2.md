## 1. 项目定位

### 1.1 项目名称

**Bidirectional Code Virtualization System**

中文名称：**双向代码虚拟化系统**。

本项目研究如何通过构造专用代码数据集，对本地代码模型进行监督微调（SFT）及后续可选的强化学习训练，使模型掌握真实代码与虚拟代码之间的双向转换能力。

项目希望让 Codex CLI
在看不到完整真实项目的情况下，基于虚拟化后的代码切片完成开发修改。修改结果由本地模型转换回真实代码，再由用户应用到本地完整项目，通过人工编译、运行和测试验证。

### 1.2 核心目标

1.  用户在本地完整项目中选择本次需要修改的代码切片。
2.  本地小模型将目标代码转换为虚拟代码，生成虚拟名称映射。
3.  本地小模型根据目标代码和修改目的生成必要的虚假上下文。
4.  Codex CLI 只针对虚拟化后的代码切片进行修改。
5.  Codex 修改完成后，本地小模型分析修改内容并完成反向转换。
6.  本地小模型处理原有变量身份、新增变量、删除变量、变量重命名及真实命名恢复。
7.  用户将模型输出的真实代码应用到完整项目，并自行编译、运行和验证。

### 1.3 项目角色

  ------------------------------------------------------------------------------------------------------
  角色                                主要职责
  ----------------------------------- ------------------------------------------------------------------
  本地小模型                          正向虚拟化、虚假上下文生成、变量身份识别、反向映射和真实代码生成

  Codex CLI                           阅读和修改虚拟化后的目标代码

  人                                  提出开发需求、选择目标切片、应用恢复后的代码、编译和验证
  ------------------------------------------------------------------------------------------------------

**本项目采用人在环（Human-in-the-Loop）方式运行。**
最终是否接受修改，由人通过真实项目的编译、运行和实际效果判断。

## 2. 总体工作流程

``` text
┌──────────────────────────────────────────────┐
│              本地完整真实项目                 │
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│ 人工开发、编译、运行和测试                    │
│ 发现 BUG 或提出新的修改需求                   │
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│ 本地小模型：正向虚拟化                        │
│ 分析切片、生成虚拟名称、建立映射、生成虚假上下文│
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│ Codex CLI：修改虚拟代码                       │
│ 只处理虚拟化后的目标切片                      │
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│ 本地小模型：反向映射                          │
│ 识别变量身份、处理变量变化、恢复真实命名      │
│ 输出恢复后的真实代码                          │
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│ 人工将恢复后的代码应用到真实项目              │
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│ 人工重新编译、运行和验证                      │
└──────────────────────┬───────────────────────┘
                       │
               仍有 BUG 或需要修改
                       └────────► 重新发起下一轮
```

### 2.1 流程说明

1.  用户正常开发本地真实项目。
2.  用户通过编译、运行或测试发现 BUG，或者确定需要修改某项功能。
3.  用户选择目标函数或代码切片，并描述修改目的。
4.  本地小模型完成正向虚拟化和必要的虚假上下文生成。
5.  系统将虚拟工作内容交给 Codex CLI。
6.  Codex CLI 根据用户的修改目的编辑虚拟代码。
7.  本地小模型读取修改前后的虚拟代码，分析变量变化并完成反向映射。
8.  系统输出恢复后的真实代码。
9.  用户自行将代码应用到完整项目。
10. 用户重新编译、运行和验证；如仍有问题，由用户提出下一轮修改需求。

### 2.2 人在环原则

-   人决定何时启动一次修改任务。
-   人指定目标代码切片和修改目的。
-   Codex CLI 修改虚拟代码。
-   本地模型负责代码转换和恢复。
-   人决定是否采用恢复后的代码。
-   人负责真实项目的编译、运行和效果验证。

本项目不追求无人干预的自动开发闭环。

## 3. 本地小模型的四项核心能力

本项目的主要研究工作集中在本地小模型。以下能力通过训练数据构造、SFT
以及后续可选的强化学习来实现和优化。

### 3.1 正向代码虚拟化

**目标：**
将用户指定的真实代码切片转换为虚拟代码，并建立稳定的虚拟名称映射。

主要任务：

-   理解目标代码中的函数、类、参数和局部变量。
-   识别需要虚拟化的项目内部标识符。
-   为标识符生成虚拟名称。
-   建立真实名称与虚拟名称之间的映射关系。
-   在名称转换过程中尽量保持代码原有逻辑和结构。
-   根据任务需要生成虚假上下文。
-   输出虚拟代码及映射信息。

示例：

真实代码：

``` python
def calculate_total(price, discount):
    result = price * discount
    return result
```

虚拟代码：

``` python
def F_001(arg_001, arg_002):
    var_001 = arg_001 * arg_002
    return var_001
```

映射信息由本地系统保存，不提供给 Codex CLI。

### 3.2 变量身份识别

**目标：** Codex
修改虚拟代码后，本地模型能够判断修改前后的变量是否属于同一变量，以及变量发生了什么变化。

主要任务：

-   识别原有变量在修改后的代码中是否仍然存在。
-   识别变量是否被 Codex 重命名。
-   识别新增变量和删除变量。
-   分析变量引用和计算关系的变化。
-   结合修改前代码、修改后代码及原映射信息判断变量身份。
-   对变量身份变化形成结构化分析结果。

示例：

修改前：

``` python
var_001 = arg_001 * arg_002
return var_001
```

Codex 修改后：

``` python
temp = arg_001 * arg_002
final_result = temp + 10
return final_result
```

本地模型需要判断 `temp` 是否对应原来的 `var_001`，`final_result`
是否为新增变量，以及原有参数是否仍保持对应关系。

### 3.3 反向代码还原

**目标：** 将 Codex 修改后的虚拟代码转换为可以放回真实项目的代码。

主要任务：

-   根据原映射信息恢复原有函数名、参数名和变量名。
-   恢复被 Codex 重命名的原有变量。
-   处理新增变量和删除变量。
-   保留 Codex 对代码逻辑所做的修改。
-   根据恢复结果生成真实代码。
-   尽量减少反向转换对 Codex 修改内容的额外影响。

反向还原不仅是简单的名称替换，还需要模型理解修改前后的变量身份及其语义关系。

### 3.4 真实命名生成

**目标：** 当 Codex
新增变量，或者修改后的代码出现新的变量身份时，本地模型能够生成符合原项目风格的真实名称。

主要任务：

-   理解新增变量在代码中的用途。
-   分析变量的计算过程和上下文。
-   参考目标代码中已有的命名风格。
-   为新增变量生成可读、合理的真实名称。
-   尽量避免名称冲突和语义不准确。

该能力通过专门构造的训练样本学习，而不是依靠固定的中性命名规则。

## 4. 虚假上下文生成

### 4.1 设计目标

Codex
只看到一个目标代码切片时，可能缺少完成修改所需的上下文。本项目由本地小模型根据当前目标和修改目的生成虚假上下文，而不是通过追加真实代码切片来补充上下文。

### 4.2 虚假上下文内容

根据任务需要，本地模型可以生成：

-   虚假函数、类和方法；
-   虚假变量和数据结构；
-   虚假依赖和调用环境；
-   虚假测试数据。

### 4.3 生成原则

-   虚假上下文由本地小模型生成。
-   虚假上下文服务于当前修改任务。
-   虚假上下文与目标虚拟代码在接口和逻辑关系上尽量保持一致。
-   虚假上下文不要求还原真实项目的完整结构。
-   Codex 缺少上下文时，不自动扩大真实代码切片范围。

虚假上下文生成能力纳入本地模型的训练和测试范围。

## 5. Python 原型系统

### 5.1 定位

Python 负责连接本地模型、虚拟工作区和 Codex
CLI，完成实验流程的调用与数据传递。第一阶段优先实现可运行的实验原型，不追求复杂的软件工程体系。

### 5.2 主要职责

1.  接收用户指定的目标代码切片和修改目的。
2.  将目标代码提交给本地模型。
3.  接收本地模型生成的虚拟代码、映射信息和虚假上下文。
4.  创建本次任务使用的虚拟工作区。
5.  启动 Codex CLI。
6.  获取 Codex 修改后的虚拟代码。
7.  将修改前代码、修改后代码及映射信息提交给本地模型。
8.  获取本地模型生成的真实代码。
9.  将恢复结果展示给用户，供人工检查和应用。

### 5.3 第一版实现范围

-   指定目标代码切片；
-   调用本地模型；
-   生成虚拟代码；
-   保存映射信息；
-   创建 Codex 工作目录；
-   调用 Codex CLI；
-   获取修改结果；
-   调用本地模型反向还原；
-   输出真实代码。

第一版可以先采用命令行或简单交互界面。

## 6. 本地模型与训练技术选型

### 6.1 基础模型

当前首选基础模型：**Qwen3-Coder-Next**。

选择它作为首选候选，是希望利用其代码理解和代码生成能力，通过专用微调使其掌握本项目需要的代码虚拟化和反向映射任务。

正式训练前需要验证模型加载、训练框架适配和推理能力。

### 6.2 微调方法

第一阶段采用：**LoRA + SFT**。

-   LoRA 用于参数高效微调。
-   SFT 用于学习明确的代码转换任务。
-   通过构造输入和标准输出，让模型学习真实代码与虚拟代码之间的转换关系。
-   通过不同类型的变量变化样本训练模型处理修改后的代码。

### 6.3 训练框架

当前确定的主方案：

  层级         技术选型                  主要用途
  ------------ ------------------------- ----------------------------------
  基础模型     Qwen3-Coder-Next          本地代码模型
  主训练框架   ms-swift                  数据处理和训练流程
  分布式训练   Megatron-SWIFT            分布式训练
  模型桥接     ModelScope MCore-Bridge   模型结构和权重适配
  底层引擎     Megatron-Core             分布式计算与训练
  第一阶段     LoRA + SFT                专用模型训练
  后续可选     DPO                       偏好优化
  后续可选     GRPO                      强化学习优化
  采样组件     vLLM                      根据后续强化学习方案决定是否采用

说明：这里的 MCore-Bridge 指 ModelScope 的 MCore-Bridge，不是 NVIDIA
Megatron Bridge。

### 6.4 兼容性验证

上述技术栈作为当前实验主方案保留，但框架支持某种模型架构或训练算法，不等于目标模型的所有训练组合都已经完成端到端验证。

正式训练前需要进行小规模验证：

1.  Qwen3-Coder-Next 能否正常加载；
2.  Megatron-SWIFT 能否完成目标模型适配和权重加载；
3.  LoRA + SFT 能否正常训练；
4.  LoRA 适配器能否保存、重新加载并正常推理；
5.  如果后续采用 GRPO，再验证采样、奖励计算和参数更新流程。

LLaMA-Factory 保留为备选和对照框架，当前不同时维护两套完整训练流水线。

## 7. 训练数据集设计

### 7.1 总体思路

本项目的关键不只是选择代码基础模型，而是构造能够让模型学会双向代码虚拟化的专用数据集。

第一阶段围绕四项核心能力组织数据，并将虚假上下文生成纳入相应任务样本。

### 7.2 Dataset 01：正向代码虚拟化

训练目标：

-   识别真实代码中的函数、类、参数和变量；
-   将真实标识符转换为虚拟标识符；
-   建立名称映射；
-   输出虚拟化后的代码；
-   在名称转换过程中尽量保持原有执行逻辑；
-   覆盖不同代码结构下的标识符虚拟化。

建议样本包含原始代码、虚拟化要求、标准虚拟代码、名称映射结果、任务类型和样本难度。

### 7.3 Dataset 02：虚假上下文生成

训练目标：

-   根据目标代码切片理解当前任务；
-   识别 Codex 修改所需的上下文类型；
-   生成虚假函数、类、变量和数据结构；
-   构造必要的虚假调用环境；
-   让虚假上下文与目标虚拟代码保持一致。

### 7.4 Dataset 03：变量身份识别

训练目标：

-   识别修改前后的同一变量；
-   识别变量重命名；
-   识别新增和删除变量；
-   识别变量拆分和合并等变化；
-   输出变量身份对应关系。

建议样本由修改前虚拟代码、修改后虚拟代码、原始映射信息和标准变量变化分析组成。

### 7.5 Dataset 04：真实命名生成

训练目标：

-   根据变量用途推断语义；
-   分析变量计算过程和引用关系；
-   参考目标代码的命名风格；
-   为新增变量生成真实名称；
-   处理多个新增变量之间的命名一致性。

### 7.6 Dataset 05：反向代码还原

训练目标：

-   根据原始映射恢复原有名称；
-   恢复被 Codex 修改过名称的原有变量；
-   为新增变量使用合理的真实名称；
-   正确处理删除变量；
-   保留 Codex 对虚拟代码所做的有效修改；
-   输出完整的真实代码。

### 7.7 数据来源

第一阶段优先使用：

1.  自动生成的合成 Python 代码；
2.  自动生成的变量改名和代码修改样本；
3.  人工设计的边界案例；
4.  许可证允许使用的开源代码；
5.  由上述代码生成的正向虚拟化与反向还原配对样本。

训练数据尽可能覆盖不同函数长度、变量数量、嵌套结构、修改方式和命名风格。

### 7.8 数据集划分

第一版建议采用：

  数据集     比例 用途
  -------- ------ ------------------------
  训练集      80% 模型训练
  验证集      10% 训练过程评估和参数选择
  测试集      10% 独立效果评估

划分时应按原始代码来源分组。同一原始函数生成的不同虚拟化版本和修改版本，应尽量放在同一个数据分组中，避免相似样本同时出现在训练集和测试集中。

### 7.9 数据格式

第一阶段建议采用 JSONL 对话数据格式。每条样本至少记录：

-   任务类型；
-   输入内容；
-   标准输出；
-   样本来源；
-   原始代码分组标识；
-   难度标签；
-   数据集版本。

正式数据 Schema 在数据集构建阶段确定。

## 8. 训练与实验路线

### 第一阶段：数据集构建

-   构建五个主题数据集；
-   编写合成代码和修改样本生成程序；
-   生成真实代码与虚拟代码配对样本；
-   检查样本质量；
-   划分训练集、验证集和测试集。

### 第二阶段：LoRA + SFT

-   使用 Qwen3-Coder-Next 作为基础模型候选；
-   使用 LoRA 进行参数高效微调；
-   使用五个主题数据集进行多任务监督训练；
-   保存训练配置、数据版本和模型权重；
-   评估模型的核心能力。

第一轮实验可以先使用一个多任务 LoRA
适配器。是否拆分为多个任务适配器，根据实验结果决定。

### 第三阶段：测试和数据迭代

重点观察：

-   正向虚拟化是否正确；
-   虚拟名称映射是否稳定；
-   变量身份是否识别准确；
-   新增变量是否能生成合理名称；
-   反向还原是否保留 Codex 的修改；
-   虚假上下文是否能够支持当前修改任务。

根据测试结果补充薄弱任务的数据，再进行下一轮 SFT。

### 第四阶段：可选强化学习

当 SFT
达到基本可用水平，并且能够构造相对可靠的自动评价标准后，再考虑强化学习。

候选方向：

-   **DPO：** 利用偏好样本，让模型学习更好的代码转换结果。
-   **GRPO：** 利用可计算的任务奖励，优化代码虚拟化和反向还原结果。

候选奖励评价内容：

-   名称映射正确性；
-   变量身份识别正确性；
-   反向还原结果正确性；
-   代码结构和输出格式符合要求；
-   合成代码测试结果。

是否采用 DPO 或 GRPO，以 SFT
测试结果和实验收益为依据，不作为第一阶段必选工作。

## 9. 实验效果评估

项目重点评估本地小模型是否真正学会双向代码虚拟化。

  评估指标             评估内容
  -------------------- --------------------------------------
  正向虚拟化准确率     是否正确转换目标标识符
  名称映射准确率       真实名称与虚拟名称是否正确对应
  变量身份识别准确率   是否正确识别修改前后的变量身份
  变量重命名识别率     是否能识别 Codex 对变量的重命名
  新增变量识别率       是否能识别新增变量
  删除变量识别率       是否能识别删除变量
  真实命名质量         新变量名称是否符合语义和命名风格
  反向还原成功率       是否能恢复正确的真实代码
  虚假上下文有效率     生成的上下文是否能够支持当前修改
  端到端任务成功率     从正向虚拟化到反向还原的整体成功情况

实验时分别评估各项能力，并进行完整流程测试。端到端测试使用模型未见过的代码样本，检查恢复后的代码是否保留

## 13. 当前方案结论

Bidirectional Code Virtualization System 的核心实验路线如下：

1.  以 Qwen3-Coder-Next 作为本地基础模型首选候选。
2.  通过构造专用训练数据集，让本地模型学习代码虚拟化和反向还原。
3.  第一阶段采用 LoRA + SFT。
4.  本地小模型负责正向虚拟化、虚假上下文生成、变量身份识别、变量变化处理、真实命名生成和反向代码还原。
5.  Codex CLI 只处理虚拟化后的目标代码切片。
6.  Python 负责串联本地模型和 Codex CLI，完成实验流程。
7.  人工将恢复后的代码应用到完整真实项目，并负责编译、运行和验证。
8.  根据实验效果决定是否进一步采用 DPO、GRPO 等优化方法。

**本项目当前最重要的实验问题，是通过专用数据构造和模型训练，让本地小模型可靠地完成代码正向虚拟化与反向还原，并能够处理
Codex 修改过程中出现的变量重命名、新增和删除等变化。**

本方案为 v0.2
实验规划文档。模型训练效果、具体训练配置及各训练组件的端到端兼容性，均以实际实验结果为准。
